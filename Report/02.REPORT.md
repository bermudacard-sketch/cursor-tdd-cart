## 1. 요약

인터뷰 메모, 실제 주문(#1107, #1042), 엑셀 검산, CS 클레임을 근거로 장바구니 할인 도메인의 테스트 가능한 계약을 추출했다. 근거가 있는 항목만 AC/INV/E ID를 부여했고, 50,000원 경계·쿠폰·배송비 등 근거 부족 항목은 OOS로 제외했다. Entity는 소계·문턱 할인·VIP 순서·입력 검증, Boundary는 빈 제출 500 오류 개선을 대상으로 한다.

## 2. 핵심 결정·산출물

| Q5 | 여러 품목을 합산할 때 품목별로 따로 할인한 적이 있나요, 아니면 항상 소계 한 번에 적용했나요? |

### 근거 레벨 분류

| 근거 | 레벨 | 내용 |
|------|------|------|
| A×3 + B×1 = 66,000 | L1 | 품목별 `단가×수량` 합 = 소계 |
| 66,000 → 59,400 (×0.9) | L1 | 소계 5만 초과 시 10% 할인 |
| #1107: 60,000→54,000 | L1 | 동일 10% 문턱 할인 |
| #1042: 48,000 무할인 | L1 | 5만 미만 시 할인 없음 |
| VIP: 59,400×0.95=56,430 | L2 | 문턱 할인 **후** VIP 5% 추가 |
| 순서: 문턱 → VIP | L2 | 적용 순서 고정 |
| 수량 -1 → 합계 0원 표시 | L0 | 잘못된 입력 처리 실패 |
| items 없음 → 500 | L0 | 빈 제출 시 서버 오류 |
| 50,000원 정확히 | — | **근거 부족** (명시적 미확인) |
| 쿠폰·배송비 | — | 언급 없음 |

### 계약표

| ID | 계약(불변식 / 에러 / AC) | 근거 레벨 | 계층 | 테스트 아이디어 | 구현 범위 |
| -- | ----------------- | ----- | -- | -------- | ----- |
| AC-1 | 소계 = Σ(단가 × 수량). 예: A(12,000×3)+B(30,000×1)=66,000 | L1 | Entity | `[(12000,3),(30000,1)]` → `66000` | Entity |
| AC-2 | 소계 > 50,000이면 `round(소계 × 0.9)` 반환 (10% 할인) | L1 | Entity | `60000`→`54000`, `66000`→`59400` | Entity |
| AC-3 | 소계 ≤ 50,000이면 소계 그대로 반환 (할인 없음) | L1 | Entity | `48000`→`48000` | Entity |
| AC-4 | VIP이고 문턱 할인 적용 후 금액 P이면 `round(P × 0.95)` 반환 | L2 | Entity | `(66000, vip=True)`→`56430` | Entity |
| INV-1 | 최종 결제액 ≥ 0 | L3 | Entity | 모든 확정 AC 입력에서 `>= 0` | Entity |
| INV-2 | 할인 적용 시 결제액 ≤ 소계 | L3 | Entity | AC-2~4 케이스에서 `pay ≤ subtotal` | Entity |
| INV-3 | VIP 추가 할인은 문턱 할인 이후 금액에만 적용 (순서: 문턱 → VIP) | L2 | Entity | `66000+VIP`: `59400×0.95` ≠ `66000×0.95×0.9` | Entity |
| E-1 | `price` 또는 `qty`가 음수이면 `ValueError` (인덱스 포함) | L0 | Entity | `qty=-1` → 예외, 0 반환 금지 | Entity |
| E-2 | `items`가 `None`이면 `TypeError` | L0 | Entity | `calculate(None)` → `TypeError` | Entity |
| E-3 | `items`가 빈 리스트이면 Boundary에서 500이 아닌 명시적 오류 응답 | L0 | Boundary | `POST` items=[] → 4xx + 메시지 | Boundary |
